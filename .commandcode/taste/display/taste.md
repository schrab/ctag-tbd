# display
- Use FONT_5X7 everywhere on the OLED display (menu, boot screen, all screens) — do not use 8x8 font in any context. Confidence: 0.80
- After the boot splash screen (ShowFWVersion), auto-show the menu by setting `inMenu = true` and calling `pages[currentPanel]->doRedraw()` in `UIMenu::Init()` — otherwise the OLED shows nothing until a button is pressed. Confidence: 0.70
- Fade the Norns-style panel bar after ~1s of inactivity in ROOT mode — do not keep it always visible. Confidence: 0.65
- The font5x7.h data is column-major (5 columns × 7 rows), despite the header comment claiming "Row-major layout". Each glyph's 5 bytes represent 5 vertical columns, reading bits 6-0 as rows 0-6 (bit 7 always 0 for interline spacing). Use `(byte >> (6 - row)) & 1` in DrawString, iterating col 0..4 (outer) and row 0..6 (inner). Confidence: 0.85
- On this SSD1306 with COM scan 0xC8, only the bit order within each page byte is reversed (bit 7 = physical top, bit 0 = physical bottom) — the GDDRAM page order is normal (page 0 = COM0-COM7 = physical top). Use `page = y >> 3` for normal page order and `bit = 7 - (y & 7)` in DrawPixel and InvertRect to flip bits so font top row maps to COM7 (physical top). Empirical verification: commit 654ea0c with `page = y >> 3` alone gave correct line order but vertically mirrored characters; adding `bit = 7 - (y & 7)` fixed the character orientation. Do NOT reverse page order (`7 - (y>>3)`). Confidence: 0.90
- Rewrite `ShowFWVersion()` to use the framebuffer (Clear + DrawString(FONT_5X7) + Flush) instead of legacy `ssd1306_display_text()` — keeps all rendering consistent and avoids mixing legacy direct I2C writes with framebuffer Flush. Confidence: 0.70
- Panel bar labels must fit within their segment width (128 / PANEL_COUNT = 32px). Six-char labels like "PARAMS" at 6px each = 36px exceed 32px and wrap, causing visible text corruption. Truncate to fit (e.g., "PARAM"). Confidence: 0.75
- Panel bar indicators should be 20px-wide rectangles at the top of the display (not squares or dotted/dashed lines). Active panel indicator is a filled rectangle; inactive panel indicators have only a 1px border (outline, not filled). Confidence: 0.75
- With the compact 3px-tall panel bar, the menu text area can fit 6 lines of FONT_5X7 text (each 8px with 1px line gap = 54px for 6 lines, leaving 7px for the bar). Do not limit to 5 lines — recalculate text layout to use the available vertical space. Confidence: 0.72
- When characters are vertically mirrored on the SSD1306 (display uses COM scan 0xC8), fix by reversing bits in DrawPixel/InvertRect (`bit = 7 - (y & 7)`) rather than reversing font row iteration order or changing GDDRAM page order. The font rendering code `(byte >> (6 - row)) & 1` iterating row 0..6 is correct and should not be changed. Empirical verification: this SSD1306 has COM7=MSB=physical top within each page, so font top row (glyph bit 6) at y+0 maps to bit 7 (COM7=physical top) with the bit reversal. Confidence: 0.85
- Before applying software display orientation fixes (bit reversal in DrawPixel, coordinate transforms), first analyze the full display pipeline from initialization through the I2C driver to the drawing primitives — the root cause may be a configurable hardware setting (COM scan direction, segment remap) set during init that can be fixed there instead of compensating in software. Confidence: 0.65
- DrawPixel and InvertRect must use IDENTICAL page and bit formulas — if they get out of sync (e.g., DrawPixel uses `page = y >> 3` while InvertRect uses `page = 7 - (py >> 3)`), each line's top and bottom halves will be drawn on opposite physical pages, causing "split and swapped" lines where the character top appears at the wrong position. After fixing one formula, verify the other is consistent. Confidence: 0.80
